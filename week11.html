Week 11b · Systematically Developing Software with AI

Engineering Agentic Workflows

Course›Week 11b

Last lecture, week 11a, covered the single agent: tools, memory and context. This one organises agentic work as a process: how agents collaborate, what the common workflow patterns are, how to choose between them, and why the check inside a loop needs criteria somebody wrote down. It closes with a software testing case study on evaluating AI-generated results. Next week takes the same question across the whole lifecycle.

Teaching unit
Weeks 9 to 12 form one unit, Systematically Developing Software with AI. Week 11a is AI agents: tools, memory and context. Week 11b is this lecture. Week 12 is AI across the software engineering lifecycle.

Learning objectives

By the end of this week you can:

  • recognise the common agentic workflow patterns and say how they differ;
  • select a suitable pattern for a software engineering task and apply it;
  • explain why evaluation inside a workflow needs explicit criteria, and what goes wrong without them.

Lecture outline

  1. One agent, and then several: how agents collaborate.
  2. Workflow or autonomous agent: what the choice actually commits you to.
  3. Five common patterns, and how to choose between them.
  4. Evaluator and optimizer in depth: the loop, a trace, four engineering decisions, and independence.
  5. Where agents sit in the lifecycle.
  6. Systematic evaluation of AI-generated results, through a software testing case study. You met testing properly in weeks 5 and 6; week 12 returns to it across the lifecycle.

Exercise 11 · Choose and apply an agentic workflow pattern

Work in your project team of three or four. Due before week 12. Plan for roughly three hours of team time. A starter script that makes one model call and one tool call is provided with the exercise, so that your time goes into the design rather than into API setup.

Part A · Recognise and compare patterns

For each of the five scenarios below, say which workflow pattern you would use and why. More than one answer can be reasonable. For at least two scenarios, name an alternative and explain the trade-off. Consider first whether a simpler, non-agentic solution would do: "no agentic workflow pattern is needed" is an acceptable answer when you justify it.

  1. About fifty bug reports in a week, spread over the UI, the database layer and performance. The team wants them analysed efficiently and turned into one prioritised report.
  2. A pull request touches a single function of twelve lines. The author wants a second opinion before merging.
  3. A feature needs a change to the data model, the API and two UI screens, and the parts depend on each other.
  4. Library documentation has to be checked module by module for examples that no longer compile.
  5. A function must be generated from a specification with six acceptance criteria, and satisfy all six before anyone looks at it.

Part B · Design a workflow for your project

Take one concrete task from the semester project and choose one of the five patterns for it. Explain why it fits, and why you prefer it to at least one alternative. Say which components take part: LLM calls, agents, tools, deterministic checks and human decisions. Say how information moves between them, and how the workflow decides it is finished. Include a simple diagram.

One guard: do not add agents the task does not need.

Part C · Apply it, and evaluate what comes out

Build a minimal working demonstration on one realistic example from your project. Save the execution trace with the intermediate outputs and decisions. Then evaluate the resulting artefacts critically: what worked, what did not, and whether the pattern was the right choice. "More than the task needed" is a valid conclusion.

What to submit

  • 1 A workflow diagram.
  • 2 An execution trace, or screenshots.
  • 3 A half-page design justification covering Parts A and B, with your evaluation of the artefacts.

Due before week 12. Feeds milestone M3.
